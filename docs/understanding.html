Mamba, and a memory that grows

What Mamba is, what the two variations in this repository change, and what the evaluation code does, with pictures you can move. Sections 1 to 7 are background, 8 describes the two tasks, 9 and 10 are the variations, 11 maps all of it to the files.

No experiment results exist yet. Everything below describes how the code works, not how well it performs.

1. The problem: remembering the past

A language model reads tokens (characters, numbers, words) one after another and predicts the next one. To do that it must remember what it already read. There are two classic ways to remember. A Transformer keeps every past token and looks back at all of them. Mamba keeps one fixed-size summary, called the state, and updates it as each token arrives.

2. The key idea: a state updated token by token

Mamba belongs to the family of state space models. The state h is a list of numbers that acts as memory. For every new token x(t), the memory first fades a little, then the new token is written in:

h(t) = decay × h(t−1) + write × x(t)        # update the memory
y(t) = read × h(t)                           # produce an output

Try it. Change the decay and the inputs and watch the memory fade. The default is the worked example: decay 0.5, write 1, inputs 4, 0, 0, 2.

input x(t)memory h(t)

The state is more than one number

Real Mamba has many channels (768 in the notebook model) and gives each channel its own N numbers of memory (N = 16 there). The N numbers of a channel forget at different speeds, fixed by A = −1, −2, …, −N: the first dimensions remember long, the last forget quickly. A layer's memory is therefore 768 × 16 = 12,288 numbers. N is the state size, and the whole project is about N.

3. What "selective" means

In older state space models the decay, write and read were fixed constants. Mamba's change is that they are computed from the current token, so the model chooses what to remember: strong writes for important tokens, almost none for filler.

NameMeaningWhere it comes from
Afixed forgetting speeds, one per memory number, always negativelearned once, not per token
Δ (dt)step size: how strongly to apply the update at this tokencomputed from the token
Bwhat to writecomputed from the token
Cwhat to readcomputed from the token
Ddirect skip from input to outputlearned once per channel
decay(t) = exp( Δ(t) × A )                          # between 0 and 1, because A < 0 and Δ > 0
h(t)     = decay(t) × h(t−1)  +  Δ(t) × B(t) × x(t)
y(t)     = C(t) · h(t)  +  D × x(t)

5. The whole model

Layers are stacked, and each has its own memory and its own parameters. The model in the notebooks has 6 layers and 5.81 million parameters. Two directions are easy to mix up: depth (which layer) and time (which token).

  • Memory while reading is 6 layers × (768 × 16 + 768 × 4) = 92,160 numbers, independent of text length.
  • The output layer shares its weights with the embedding ("tied").
  • While generating, one token goes up through the 6 layers and each layer updates its memory. While training, all tokens are processed at once (next section).

6. Training versus generating: the scan

The update looks sequential (h(t) needs h(t−1)), but it can be computed for many tokens at once with a scan, a running calculation built from cumulative sums. Our code does this in chunks of 8 tokens.

This is why N costs real time and memory in our code: the scan builds temporary tensors of shape (batch, length, 768, N). We measured that the state-dependent part is 80 to 100% of a training step. The official Mamba hides it in a custom GPU kernel; ours is plain PyTorch, slower and heavier but readable and easy to change.

7. Why copying is hard for Mamba

Task: read a random string, then repeat it exactly. To copy n symbols, all n must still be in memory when it is time to write them out. A Transformer simply looks back. Mamba only has its fixed state. The paper this project follows (cot.pdf) shows that Mamba's copying gets worse as strings get longer or the model gets smaller.

Transformer: every symbol stays available
Mamba, toy memory with 12 slots (symbols past the limit are overwritten)

A toy picture of the idea only. A real state is a compressed summary, and its true capacity depends on N, the width and the depth; no capacity number is claimed here.

The project's idea: instead of one fixed memory size for the whole text, make the memory larger as the text gets longer, so short stretches stay cheap and the capacity is there when it is needed.

8. The two tasks we test on

Both come from published code that we adapted. In both, the model is trained to predict the next token, then scored on how exactly it reproduces the right answer.

8.1 Copy task

Symbols: $ start, | separator, . end, * padding. The loss is counted only on the answer and the end symbol (the first half is random, so predicting it teaches nothing). Green chips are where the loss is counted.

Scoring is "teacher forcing": the model is fed the correct text and we check its prediction for each next token. str_acc counts an example as right only if the whole answer is right; char_acc is the fraction of correct letters. Both are reported per string length. Training uses strings of 5 to 40 letters, one example per context.

8.2 Chain of thought: longest increasing subsequence

The input is a list of numbers; the answer is the length of the longest strictly increasing subsequence. With chain of thought the model writes the working out first. That gives it a scratchpad, but makes the sequence about twice as long. A sequence only counts as correct if every token after the first <sep> is right.

9. Variation 1: state size changes with depth

Standard Mamba uses the same N in every layer. var1 keeps the total fixed and spreads it unevenly: small N in early layers, large N in late layers. Within a layer N does not change over time. The hypothesis: early layers do local work the convolution already covers, while late layers must carry long-range information.

10. Variation 2: state size grows along the sequence

var2 changes N over time instead of depth. The state starts small and gets bigger at chosen token positions, up to a cap. A schedule is a list of start_token:N pairs; the last N is the cap, so memory is bounded. The same schedule is used in every layer. Edit it, then move the slider.

What it costs

Counts of state numbers per channel, not measured time. They show the shape of the saving, which shrinks as texts get long and the state sits at the cap.

How the code does it

When the size grows, the new memory numbers are appended with the value zero and the old ones are kept exactly. Nothing is erased or converted.

  • Parameters are allocated for the cap. A late stage may use all of them; an early segment uses the first N of each row. So var2 has more parameters than a standard N = 16 model (roughly 11 to 16% more) and the same number as a standard model at N = cap.
  • Cost follows the schedule. In a segment with small N the scan and the projection handle only N numbers per channel.
  • Everything else is the standard model: embedding, norms, convolution, gating, projections, output layer, and the update formula. GrowingMambaLM builds a normal model and swaps each layer's SSM for a GrowingSSM (mamba_growing.py, 96 lines).

What is tested

  • A one-stage schedule gives exactly the standard output.
  • A multi-stage schedule equals a reference that always uses the full size but zeroes write and read for not-yet-active dimensions.
  • The model is causal, also across a switch; every parameter gets gradients, including the late ones.

Limits: no token-by-token generation yet, no --compile support, and the cost savings are designed but not yet benchmarked. There are no accuracy results.

Choose the model in either harness; everything else (data, loss, optimiser, scoring) is identical, so differences in results come from the memory design only.

--model mamba                                   # standard Mamba
--model mamba_var1 --state_schedule linear      # state size changes with depth
--model mamba_var2 --schedule "0:8,16:16,32:32,64:64"   # state size grows along the sequence

The planned comparison: for each string length, var2 against standard Mamba with constant N = 8, 16, 32, 64. The question is at which lengths var2 reaches the accuracy of the large constant models (which have the same parameters as var2 at N = 64) while using less memory and compute on average, or beats a constant model of the same average cost.
